# RAG 知识库设计说明

> 术语速览（面向零基础）：
> - **RAG**（Retrieval-Augmented Generation，检索增强生成）：让 LLM 回答前先去知识库里查资料，把查到的内容连同问题一起给模型，减少胡编（幻觉）。
> - **Embedding / 向量**：把一段文字变成一串数字，语义相近的文字数字也相近，用来做"意思层面"的搜索。
> - **BGE-M3**：开源中文向量模型（BAAI 出品），"M3"指多语言/多粒度/多功能。负责把文档和问题都变成向量。
> - **BM25**：经典关键词检索算法，按词出现频率和稀有程度打分。向量检索管"意思像"，它管"字面准"（如型号 SKU-10001、专有名词）。
> - **ChromaDB**：轻量向量数据库，存向量并支持"找出最相似的 k 条"。
> - **Chunk（分块）**：把长文档切成小段再入库，检索时只取相关的小段，省 token 且更准。

## 一、设计目标

| 指标 | 目标值 |
|---|---|
| 混合检索命中率（hit@5） | ≥ 85% |
| 检索召回方式 | 向量（BGE-M3）+ BM25 混合 |
| 知识库规模 | 目标 10 万+ 商品（当前示例数据 1 件） |
| 单次检索延迟 | < 500ms |
| 检索质量基线 | 纯关键词检索（用于对比实验，预期提升约 30%） |

## 二、知识域划分与 Collection 映射

检索粒度按**知识域**而非文档类型划分：同一域的文档入库到同一个 Collection，检索时只查相关知识域，减少跨域噪音。

源文档 6 类 → ChromaDB 3 个 Collection，映射规则：

| rag_docs 目录 | doc_type | 入库 Collection | 说明 |
|---|---|---|---|
| products/ | product | product_knowledge | 商品详情 |
| specs/ | spec | product_knowledge | 规格参数，与详情同域 |
| guides/ | guide | product_knowledge | 选购指南，导购语义同域 |
| faq/ | faq | product_knowledge | 常见问答，同域 |
| policies/ | policy | policy_knowledge | 平台政策，独立域（客服高频，误召回代价高） |
| reviews/ | review | review_knowledge | 用户评价，独立域（避免口语化评价污染商品咨询） |

依据：
1. 商品咨询 / 选购推荐意图 → 查 `product_knowledge`（详情+规格+FAQ+指南一次可召回）
2. 售后、物流、退换货意图 → 查 `policy_knowledge`
3. "口碑怎么样 / 有什么缺点"类查询 → 查 `review_knowledge`

> 路由到哪个 Collection 由 Agent 状态机的意图识别节点决定（见 [03_agent_workflow.md](03_agent_workflow.md)），本文件只定义知识库侧规则。

## 三、元数据规范

入库时每个 chunk 携带元数据（ChromaDB metadata 字段），用于过滤与过滤式检索：

| 字段 | 类型 | 说明 | 示例 |
|---|---|---|---|
| doc_id | string | 文档唯一ID | prod:SKU-10001 |
| doc_type | enum | product/spec/faq/policy/review/guide | spec |
| product_id | string | 关联商品ID，非商品类为空 | SKU-10001 |
| category | string | 商品类目（一级） | 数码/耳机 |
| brand | string | 品牌，用于按品牌过滤 | SoundCore |
| source | string | 数据来源文件 | specs/SKU-10001.json |
| updated_at | string | 更新时间 | 2026-09-12 |
| version | string | 版本号，增量更新用 | v3 |

用途示例：用户问"SoundCore 的耳机"→ 过滤 `brand=SoundCore` 后再向量检索；价格类问题只信 spec 文档，避免 review 里的旧价格干扰。

### 元数据过滤的两个坑（2026-09-13 实测）

1. **不能独占过滤**：faq / guide / policy 这类非商品文档的 `product_id` 是空串，
   `where={"product_id": "SKU-10001"}` 会把它们整体排除。而"耳机保修多长时间"的正解
   恰恰是 faq 文档——独占过滤会把已经答对的问题改成答错。所以实现的形态是
   **重排 + 补充**（`retriever.search_with_product_focus`）：先无过滤拿到全量 top-5
   （召回上界不变），把该商品的块提到前面；只有当该商品没占住前排时才补一次带锚定的
   检索。**任何时候都不会丢掉无过滤的结果**。
2. **词法置信门要跟着放宽**：这道门（仅 BM25 支持时要求 ≥2 实词相交）是想拦
   "量子涨落对股市的影响"这类噪声，但它也会误杀正解——"打游戏延迟高不高"与正解块
   只有"延迟"一个实词相交。带 `where` 时放宽到 1 个：断言"这块资料属于用户正在聊的
   商品"是第二重独立证据，叠加起来足够可信。**放宽只作用于带过滤的那次检索**，
   无过滤路径的门槛一动没动，噪声 query 仍返回空。

## 四、分块策略（Chunking）

> 下表是设计依据；三种切法的实测对比（typed vs 定长 512/256）见 §七第三轮。

| 文档类型 | 分块方式 | 理由 |
|---|---|---|
| products/*.md | 按 `##` 二级标题切 | 每个卖点/场景天然独立 |
| specs/*.json | 整文件一个 chunk（1 件商品 < 500 token） | 结构化数据不宜拆散 |
| faq/*.md | 一问一答一个 chunk | 问答对是最小检索单元 |
| policies/*.md | 按 `##` 切，父标题拼进正文 | "特殊品类规则"脱离"退换货政策"会歧义 |
| reviews/*.md | 好/差评关键词各自一块，摘录跟各自块 | 正负面分开，避免召回混淆 |
| guides/*.md | 按 `##` 切 | 每个"按需求选"小节独立成篇 |

通用规则：
- chunk 上限 512 token，超出再对半切
- 每个 chunk 头部拼接商品名 + 品牌：`【无线降噪蓝牙耳机 Pro | SoundCore】正文...`（提高向量区分度）
- spec 类 chunk 的 json 展平为 "键: 值" 文本行再入库

## 五、混合检索流程

```
query
  ├─→ 向量检索：BGE-M3(query) → ChromaDB top-k（k=5）
  ├─→ BM25 检索：同一 Collection 倒排索引 top-k
  ↓
RRF 融合（Reciprocal Rank Fusion，按两边排名取倒数求和）
  ↓
按 doc_type 加权（咨询意图：spec > product > faq > guide）
  ↓
top-5 进入 LLM 上下文
```

> RRF 通俗版：两个渠道各给候选排名，两条都排前面的最终排名高。不用调分数阈值，工程上省事且稳。

兜底规则（与状态机衔接）：
- RRF 融合后最高分 < 阈值 γ（初始设 0.02，**实测已调至 0.012**，理由见 §七）→ 回复"暂无相关信息" + 转人工入口
- 命中率统计埋点：**已实现**，见 [`app/retrieval/telemetry.py`](../app/retrieval/telemetry.py)，
  每轮 RAG 落一行 `data/logs/retrieval.jsonl`（query / 召回块 / 排序分 / 引用判定 / outcome / 耗时）

### 关于"最终是否被 LLM 引用"：这是代理指标，不是准确率

原文写"用于算 85%+ 指标"，这个说法要收窄——**它算不了 hit@5**，两者回答的是不同问题：

| | 回答的问题 | 依据 | 当前值 |
|---|---|---|---|
| 本埋点 | 召回的块**用没用上** | 字符 4-gram 重叠率（推理时零成本） | 记录在 `citation` 字段 |
| 评测集 hit@5（§七） | 该召回的块**召回了没有** | 50 条**人工标注** | 100% |

两个已知盲区，写在代码里也写在这里，免得被当成准确率引用：

1. **度量的是"抄了多少字面"，不是"用了多少资料"**：模型把"续航 30 小时"改写成"能撑一天多"，
   字面重叠接近 0，判为未引用。2026-09-13 同一条 query
   （「SKU-10001 这耳机口碑怎么样 有什么缺点」）前后跑两次真实 LLM，两次**召回完全相同**
   （5 个 chunk_id 与 rrf_score 逐一对齐），但引用块数一次是 **1**、一次是 **3**：

   | 跑次 | 各块重叠率 | 判为引用 |
   |---|---|---|
   | 第一次 | 0.1154 / 0.0333 / 0.0909 / 0.2364 / 0.0211 | 1 块 |
   | 第二次 | 0.2500 / 0.2333 / 0.1023 / 0.2182 / 0.0211 | 3 块 |

   差异全在措辞：第二次把块里的「（312 次）（198 次）」原样抄了，第一次改写成自然语言。
   **会低报，且低报程度随措辞波动——同一 query 跨轮差 3 倍。** 分块少时反而稳：
   同期的「冲锋衣怎么洗」轮只有 1 块真正被用，两次都准确命中那一块、其余全 0。
   **别把单轮的这个数当质量结论。**
2. **看不见"该召回而没召回"**：盲区在检索侧，本埋点只观测生成侧，压根不覆盖。

另外必须扣掉"本轮样板文字"：chunker 给每个块头部拼了商品锚点
（`【SKU-10001 无线降噪蓝牙耳机 Pro | SoundCore】正文…`），不扣的话回复提一句商品名就会把
该商品**所有**块判成被引用——系统性虚高，且正好虚高在最热门的商品上。判据是"在本轮一半以上
的块里都出现"。对策不是去调那个常数：每块原始重叠率都落在记录里，要重新划线拿旧日志离线
重算即可，不必重跑 LLM。

## 六、更新与版本

- 增量入库：同一 `doc_id` 新 version 覆盖旧 chunk（按 metadata `doc_id` 先删后插）
- 商品价格/库存不进 RAG——属实时数据，只经 Function Calling 查询（见 [02_tool_definitions.md](02_tool_definitions.md)），RAG 里的 spec 只存"发布时快照"并标注 updated_at
- 全量重建：脚本一键重跑（每个 Collection 独立重建，互不影响）

## 七、评测方案（怎么证明 85%+）

1. 构造评测集：50 条真实客服话术改写的问题，人工标注每条应命中的 doc_id（按"可接受文档集合"标注，实现见 `app/retrieval/eval.py`）
2. 指标：hit@5（top-5 里包含正确文档即为命中，判到文档级）
3. 对照组：纯 BM25 / 纯向量 / RRF 混合，三者跑同一评测集
4. 预期：混合 ≥ 85%，比纯关键词提升约 30%（即纯 BM25 约 55-65%）

### 首轮实测结果（2026-09-13，50 条）

| 检索方式 | hit@5 |
|---|---|
| 纯向量 | 90% |
| 纯 BM25 | 94% |
| RRF 混合 | 96% ✅（≥85% 达标） |

### 第二轮：加话题商品锚点（2026-09-13，同一评测集）

评测集每条增补一个标注——"这句话发出时用户正在聊哪件商品"（`eval.QUERY_FOCUS`，
50 条中 22 条有锚点），等价于 Agent 层的 `product_id` 槽位。第四路 `focus` 走的
就是 Agent 真实会走的路径（`search_with_product_focus`）：

| 检索方式 | hit@5 | 未命中 |
|---|---|---|
| 纯向量 | 90% | 5 |
| 纯 BM25 | 94% | 3 |
| RRF 混合 | 96% | 2 |
| 混合 + 话题商品锚点 | **100%** | 0 |

相对混合 +2 条且**零倒退**（混合命中的 48 条全部保住）。这不是
"把阈值再放松一轮"换来的分数：无过滤路径的三路结果与首轮逐条一致，多出来的 2 条完全
来自"知道用户在问哪件商品"这条新增信息。

> 数字别当通用结论看：这份评测集只有 50 条、8 件商品，100% 更接近"机制有效"的
> 证据，而不是"检索已经没有提升空间"。真实语料上，锚点抽错反而会拖累—所以判定
> 标准定的是**相对混合非负**而不是绝对值。`eval.py` 每次都会打印这个差值。

实测推翻/修正了三处设计假设（教训已回写进代码注释）：

1. **兜底阈值 0.02 过严**（§五）：会把"向量路超距、BM25 单路精确命中"的 query（如"压胶洗完会起泡吗"）整批误杀为"暂无信息"。已降为 0.012，并新增词法置信门——仅 BM25 支持的候选须与 query 相交 ≥2 个实词，专拦停用词级别的词法巧合（"量子涨落对股市的影响"实测靠"对/的"攒出 4.76 分，停用词过滤后归零）。BM25 两侧统一走停用词过滤的 `_tokenize`。
2. **doc_type 加权不宜惩罚 faq/guide**（§五）：guide 0.8 的衰减把"预算三百以内"的指南文档挤出 top5。加权只保留 spec 1.3（价格只信 spec 的原意），其余一律 1.0。
3. **chunk 锚点必须含商品ID**（§四）：评价文档的 H1（含 SKU 号）不入块，用户报型号提问时 BM25 无从匹配。锚点改为 `【SKU-10001 无线降噪蓝牙耳机 Pro | SoundCore】`。

剩余 2 条 miss 的归因修正：原以为都是"报了型号的评价类查询"，实测只有一条卡在
词法门上（"打游戏延迟高不高"只有"延迟"一个实词与正解块相交，见 §三坑 2）；另一条
"这款耳机有什么缺点"才是真的靠锚定——裸检索时 SKU-10001 的评价块排不进 top5，
锚定后一次补检索直接把它提到了第一。两条都不是检索器该打的补丁。

### 落地位置与代价

- **检索器**只提供能力：`search(where=...)` + `search_with_product_focus()`，
  不关心 product_id 从哪来。
- **Agent 层**决定何时锚定：`intent` 抽 `product_id` 槽位（字面型号走正则，模糊
  指代走 LLM + 注入的商品目录，且结果必须落在目录内——幻觉出来的 ID 会把正确答案
  筛成空集）；`Session.current_product_id` 记住跨轮话题商品，下一句可以省主语。
- **代价**：锚定后该商品没占住前排时会多一次检索（翻倍的那部分开销），8 件商品的
  演示规模下无感；真实规模下值得给这条补检索加一层缓存
  ——同 (query, product_id) 组合短期复用即可。

**评价域路由（已闭环，2026-09-13）**：`RAG_MODES` 原先把 product_consult /
param_compare / recommendation 三个意图全部指向 `product_knowledge`，没有任何意图
会绕到 `review_knowledge`——"XX 口碑怎么样"会拿商品详情去答。§二第 3 条规定的
评价域路由当时没有落地。

补法是**新增第 8 个意图 `review_consult`**（不选"在意图内按关键词二次判定"）：
两者查的不是同一个库，并进去就得在节点内部塞规则，规则难维护，而且会让
`product_consult` 的置信度语义分裂——一半来自模型、一半来自规则。
`review_consult` 同时进了 `FOCUSABLE`（评价按 SKU 存、doc 带 product_id，
是标准的单商品锚定场景）。边界靠提示词里一对例子固定：
"多久充一次电"是咨询（客观参数），"续航够用吗"是评价（使用体验）。

### 第三轮：排序类指标 + rerank 精排 + chunk 策略对比（2026-09-17）

hit@5 在第四路（锚点）上已顶到 100%，指标饱和——"进没进前五"问不出
新问题。本轮给 `eval.py` 补了两个排序类指标：**hit@1**（正确文档排第一的
比例）与 **MRR**（首个正确文档排名的倒数平均），四路基线在同一评测集重跑：

| 检索方式 | hit@5 | hit@1 | MRR |
|---|---|---|---|
| 纯向量 | 90% | 70% | 0.776 |
| 纯 BM25 | 94% | 68% | 0.788 |
| RRF 混合 | 96% | 72% | 0.809 |
| 混合 + 话题商品锚点 | 100% | 88% | 0.926 |
| 混合 + bge-reranker-v2-m3 精排 | 96% | **74%** | **0.826** |

第五路是两阶段检索的落地（`app/retrieval/reranker.py` + `retriever.search_reranked`，
`SHOPMATE_RERANK=1` 开启）：混合初检 top-20 → cross-encoder 精排 → top-5。
结论三条：

1. **指标换对了**：hit@5 顶满后 rerank 仍有提升（hit@1 +2pp、MRR +0.017），
   且相对混合非负——若掉分说明排序逻辑有 bug，这里没有。
2. **收益温和是评测集的属性**：50 条里多数 query 正解本来就排前一两名，
   精排的作为是"把第 3~5 名的正确答案顶上去"，这种 case 在这份集子里
   只有零星几条。真实语料（初检更脏）上收益空间更大。
3. **cross-encoder 与话题锚点重排是两回事**：前者是模型精排（问题+段落
   拼接过模型出分），后者是业务规则（话题商品的块提前）。表格里两者
   不可互相替代——focus 依赖"知道用户在聊哪件商品"这条额外信息。

**chunk 策略对比**（`app/retrieval/chunk_compare.py`，三种切法各建独立库，
同评测集，判到文档级）：

| 策略 | 块数 | 平均块长 | vector hit@5 / hit@1 / MRR | bm25 同 | hybrid 同 |
|---|---|---|---|---|---|
| typed（现状，按类型切） | 124 | 149 字 | 90% / 70% / 0.776 | 94% / 68% / 0.788 | 96% / 72% / 0.809 |
| fixed512（定长无视结构） | 42 | 393 字 | 86% / 62% / 0.718 | **68%** / 42% / 0.537 | 98% / 72% / 0.830 |
| fixed256（定长无视结构） | 86 | 206 字 | 94% / 72% / 0.807 | 94% / 62% / 0.755 | 98% / 76% / **0.857** |

读法（比数字本身重要）：

- **定长大块会弄残 BM25**：fixed512 的词法路从 94% 崩到 68%——一个块塞
  进多个主题后，词被稀释，IDF 区分度下降。这正是"分块粒度是词法检索
  生命线"的量化证据。
- **fixed256 在本文档级口径下反超 typed**，但要打折看：判到文档级时，
  同一文档块越多、进 top5 的机会越多（86 块 vs 124 块的分布差异也会
  影响），这里的优势部分来自口径而非纯质量；且 typed 块的标题归属/
  节边界是为**生成侧**的引用粒度服务的（§四），检索指标量不到这部分。
- **选型维持 typed**：检索侧 typed 与 fixed256 差距在噪声量级（MRR
  0.809 vs 0.857），而结构化块在生成侧（引用指到节、答案自含上下文）
  的收益是 fixed 策略结构上给不了的。若未来只做检索不做生成（如纯
  搜索接口），fixed256 是值得考虑的便宜方案。

### 生成侧评测：RAGAS（15 条试跑已出数，异族裁判）

检索指标只能证明"找得准"，证不了"答得没编"。生成侧引入 RAGAS
（`app/retrieval/ragas_eval.py`），三个指标：faithfulness（忠于资料否）、
answer_relevancy（答到点否）、context_precision（相关资料排得靠前否，
与 MRR 互证）。

**裁判是 qwen-plus（阿里云百炼），与生成侧 DeepSeek 不同族**——这一条是
分数可用的前提：同族裁判是让模型评自己，有自评偏好，分数虚高。脚本里
`_pick_judge()` 有 DASHSCOPE_API_KEY 就用 Qwen，没有才退回 DeepSeek 并打
警告横幅，**回退模式出的分不能写进文档**。

#### 实测（2026-09-17，评测集前 15 条，50 条标注已人工填齐）

| 指标 | 分数 | 可信度 |
|---|---|---|
| faithfulness | **0.871** | 可用 |
| context_precision | **0.812** | 可用（15 条里有 1 个 0） |
| answer_relevancy | 0.542 | **不可信，见下** |

#### ⚠️ answer_relevancy 这 0.542 别当结论用

15 条里出现了 **4 个精确的 0.000**，而逐个查下去，它们**不是"模型答得差"**：

- **不是空回复**（我一度这么以为，是错的——`ragas_results.json` 根本不存
  `response` 字段，`.get('response','')` 读的是默认值，于是 15 条**全部**
  显示为空串，而我只打印了零分那几条，正好把错觉坐实）。
- **不是 n=1 抽掉了平均**。试过对 Qwen 放行 `n`，日志里照样是
  `LLM returned 1 generations instead of requested 3`——langchain 这条路径
  压根没把 n 传进请求体，剥与不剥实测等价（同一批样本两次打分逐位相同）。
  想要那层抽样平均得绕开 langchain 直接用 ragas 的 `llm_factory`。
- **是生成侧的不确定性传导过来的**。RAG 生成用 `temperature=0.3`，同一 query
  每轮回复都不同；反解问题（用答案反推问题，再与原问题比向量余弦）对措辞
  敏感，某一份回复会让反解跑偏、余弦塌到 0。同一条 query 复跑：一次 0.000、
  一次 0.8127（回复 175 字，反解问题问得又准又对）。

**所以这个指标的分数由"这一轮生成恰好长什么样"主导，不是由模型质量主导。**
要报它就得报分布（多跑几轮看区间），不能报单轮均值。faithfulness 和
context_precision 没有这个反解步骤，不受影响。

#### 落地时踩平的坑

- ragas 0.4.3 与 langchain-community 0.4 不兼容（降 0.3.31）
- DeepSeek 端点不支持 n>1（400），须在请求层剥掉 n 参数
- BGE-M3 必须在进 RAGAS 事件循环前预热，否则 transformers 联网查
  chat template 挂起
- 裁判和生成两侧的 HTTP 客户端都得显式 `trust_env=False`，否则会去读
  Windows 注册表里的系统代理并报一句与网络无关的 TLS EOF
  （详见 `app/llm/client.py` 的 D5 与 README「环境坑」）
